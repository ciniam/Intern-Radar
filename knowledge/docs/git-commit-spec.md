## 适用范围

后端、前端、脚本的所有提交，含临时分支。

## 格式

```
类型(范围): 一句话说明

补充说明为什么这么改，可选
```

## 类型取值

| 类型 | 用途 |
| --- | --- |
| feat | 新增功能 |
| fix | 修复缺陷 |
| refactor | 不改变行为的重构 |
| docs | 只改文档 |
| chore | 构建、依赖、配置等杂项 |
| test | 只改测试 |

范围写模块名，例如 adapter、report、learn、frontend。

## 硬性要求

1. 一句话说明用祈使句，结尾不加句号，控制在 50 个字符以内。
2. 一条提交只做一件事，功能改动和格式化不要混在一条里。
3. 不要写「修改」「更新」「优化」这类没有信息量的描述。
4. 涉及接口变更时，在补充说明里写明受影响的接口路径。

## 反例

```
update
修改了一些问题
feat: 加了很多功能
```

## 正例

```
fix(zentao): 会话失效时识别登录页特征，避免静默返回零条数据
feat(learn): 新增文档检索工具与读取工具，问答返回引用清单
```

## 与日报的关系

工作日报里的「今日完成」需要给出对应的提交短哈希，因此提交粒度不要太粗，
否则一条提交会同时对应多个不相干的工作点，报告里无法引用。
